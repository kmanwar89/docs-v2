Wildcard certificates allow you to secure unlimited subdomains with a single SSL certificate, eliminating the need to generate individual certificates for each subdomain. Pangolin uses Traefik's built-in Let's Encrypt integration to automatically manage these certificates.

Before setting up wildcard certificates, you must have a domain that you own and control. You must also have access to the DNS records for this domain.

Since Pangolin uses Traefik as a reverse proxy, it has built-in support for Let's Encrypt certificates. This allows you to easily secure your Pangolin instance and all proxied resources with HTTPS. Let's Encrypt provides free SSL certificates, which are automatically renewed.

If you used the default settings during installation, your Traefik instance should be set up to use `HTTP-01` challenge for certificate generation. This challenge is the easiest to configure and requires that the Traefik instance be accessible from the internet on port 80.

It is highly recommended that you read the official Traefik documentation on ACME and Let's Encrypt before proceeding.

## Benefits of Wildcard Certificates

- Secure unlimited subdomains with one certificate, reducing management overhead.
- Add new subdomains without waiting for certificate generation.
- Reduce Let's Encrypt rate limit impact by using fewer certificate requests.

### Examples

- A wildcard cert `*.example.com` could protect:
  - `api.example.com`
  - `blog.example.com`
  - `dashboard.example.com`
- Another wildcard `*.subdomain.example.com` could protect:
  - `api.subdomain.example.com`
  - `blog.subdomain.example.com`

The rate limits for Let's Encrypt are per domain. Using a wildcard certificate reduces the number of domains you have, which can help you avoid hitting these limits.

## Setting Up Wildcard Certificates

Wildcard certificates require switching Traefik from the default HTTP‑01 challenge to the DNS‑01 challenge. The steps below walk through the full configuration process using Cloudflare as an example, though any supported DNS provider will work.

---

### 1. Create a DNS Provider API Token

Before configuring Traefik, generate an API token with permissions to manage DNS records.

#### Cloudflare Example

Create a token with:

- Zone → DNS → Edit
- Zone → Zone → Read

Save the token—you will add it to your environment shortly.

For other DNS providers, refer to their API credential documentation.

---

### 2. Update Traefik Configuration for DNS Challenge

Navigate to the Traefik configuration directory:

config/traefik/

You will update two files.

#### 2a. Update `traefik_config.yml`

Replace the HTTP challenge with a DNS challenge:

Before:

httpChallenge:
  entryPoint: web

After:

dnsChallenge:
  provider: "cloudflare" # or your DNS provider

#### 2b. Update `dynamic_config.yml`

Locate the router definition for your main domain (e.g., next-router for host.example.com && !PathPrefix) and add:

domains:
  - main: "example.com"
    sans:
      - "*.example.com"

This instructs Traefik to request a certificate for both the apex domain and all subdomains.

---

### 3. Create a `.env` File for DNS Credentials

In the same directory as your compose.yml file, create:

CLOUDFLARE_DNS_API_TOKEN=your_cloudflare_api_token_here

This keeps sensitive credentials out of version control and allows Docker Compose to load them automatically.

---

### 4. Expose the API Token to the Traefik Service

Ensure the Traefik service in your docker-compose.yml loads the environment variable:

services:
  traefik:
    image: traefik:v2.5
    environment:
      - CLOUDFLARE_DNS_API_TOKEN=${CLOUDFLARE_DNS_API_TOKEN}

---

### 5. Remove Existing ACME State

If Traefik has previously issued certificates, delete the existing acme.json file so Traefik can request new certificates using the DNS challenge:

cd config
rm acme.json

---

### 6. Start the Stack

Bring up the services:

docker-compose up -d

Traefik will now request wildcard certificates using the DNS challenge. You can monitor progress in the Traefik logs:

docker logs -f <traefik_container_name>

---

This setting will try to encourage Traefik to request one wildcard certificate for each level of the domain used by your existing resources.

Example: If you have two resources blog.example.com and blog.subdomain.example.com, Traefik should try to request a wildcard certificate for *.example.com and *.subdomain.example.com automatically for you.

To learn more about provider‑specific configuration options, refer to the Traefik documentation.

Traefik supports most DNS providers. You can find a full list of supported providers and how to configure them in the Traefik documentation on providers.

## Verify it Works

You can ensure Traefik doesn't try to use the old certs by deleting the previously used acme.json file. This will force Traefik to generate a new certificate on the next start.

1. Start the stack  
   Start the stack and watch the logs. You should notice that Traefik is making calls to your DNS provider to create the necessary records to complete the challenge.

2. Check logs  
   For debugging purposes, you may find it useful to set the log level of Traefik to debug in the traefik_config.yml file.

3. Test new resource  
   After Traefik is done waiting for the cert to verify, try to create a new resource with an unused subdomain. Traefik should not try to generate a new certificate, but instead use the wildcard certificate. The domain should also be secured immediately.

4. Verify certificate  
   You can also check the volume (in the example above at config/letsencrypt/) for the correct certificates. In the acme.json file you should see something similar to the following. Note the "*." in the domain.

{
  "Certificates": [
    {
      "domain": {
        "main": "example.com",
        "sans": [
          "*.example.com"
        ]
      },
      "certificate": "...",
      "key": "...",
      "Store": "default"
    }
  ]
}

## Troubleshooting

Certificate not generating:
- Verify DNS provider credentials are correct
- Check that API token has proper permissions
- Ensure domain ownership and DNS access
- Review Traefik logs for specific error messages

DNS challenge failing:
- Verify DNS provider is supported by Traefik
- Check API token permissions and scope
- Ensure DNS propagation has completed
- Review provider-specific configuration

Old certificates still being used:
- Delete the acme.json file to force new certificate generation.
